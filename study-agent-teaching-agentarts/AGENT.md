# 学习辅助 Harness：设计讨论约定

## 项目背景

- 当前处于设计阶段，目标是设计一款辅助人类学习的 harness。
- 团队已提供首轮功能草稿及队友的开发手册，正在逐轮评审；不要将助手提出的方向当作已经确定的需求。
- 本文件用于保留本次讨论约定，供后续继续设计时查阅。

## 已确认的长期产品目标

- 项目的参赛起点是第十一届华为 ICT 大赛（2026—2027）中国区创新赛赛题二。
- 项目应在比赛结束后继续维护、持续更新，能够被真实使用；团队也希望亲自使用并据此打磨产品。
- 后续可以在持续改进的基础上参加其他比赛，复用已经积累的项目能力。
- 产品应具备独立性，并希望能够安装在不同终端，不将华为云或其他单一厂商的专有服务设为不可替换的依赖。
- 为满足赛事要求，可以转换、修改和接入必要的平台能力，但应保留项目原本的核心基座。
- 讨论具体架构时，应同时评估长期维护价值和当前赛事交付要求，不能直接把赛事指定平台当成产品永久架构。
- 用户已接受联网调用可替换的模型服务；完全离线不是当前硬要求。
- 首版优先电脑端，从网页应用开始；后续可安装客户端及其他终端的范围尚待确定。
- 哪些功能及数据必须本地保存、“核心基座”的具体边界，仍需结合网页首版进一步讨论。
- 本项目从诞生起即面向本届华为赛事，当前无需围绕“将其他赛事旧作品直接复用”展开；赛后长期发展仍是明确目标。

## 当前功能草稿与参考材料

- 初步面向普通本科大学生及其他自由学习者，暂不以研究者为主要对象；这一人群是否足够聚焦、方案是否有效，仍需验证。
- 用户选择的主要学习方向是阅读教材或课程资料，理解概念、建立联系并自测；具体课程与资料尚未选定，验证安排暂后置。
- 用户确认首版同时提供有教材主线和无主线学习的完整入口。无主线学习从用户的目标出发，在可用资料较多但路线未形成时，由 teacher 推荐候选节点，经用户选择逐步形成可续学的路线。用户只给目标也能开局，teacher 可主动找可靠的公开资料，候选节点附上可回查的出处。
- 用户确认同一学习目标下，探索期间选定想跟着学习的教材，可以在现有学习图上新增教材主线。原探索记录和里程碑可在教材路线中引用。用户倾向直接复用目标和学习要求相同的旧节点，按教材补上对应内容和出处。
- 用户目前混合使用电脑与纸上／平板记录，愿意把关键步骤交给系统。不能假定系统能持续看到全部草稿或学习活动。
- 用户要求首版只实现一种学习内容输入，目前倾向键盘打字。用户仍可在纸上、数位板或平板做草稿，必要时只提交想让 teacher 看的一段。
- 用户已确定首版优先把 harness 里的学习笔记以 Markdown 导出到 Obsidian，暂不做已有 Obsidian 库的导入，双向同步留待后续。正文与节点、来源、进度等状态分别保存是助手的实现建议。
- 用户希望设置 teacher 与 keeper 两种不同职责的 agent；具体边界、编排和实现尚未冻结。
- 用户已明确认可当前产品主张：让用户组织和重组自己的学习过程，在主线、兴趣支线与跨学科联系之间自由移动，并持续获得适合自己的教学辅助。节点化、branch／merge 与跨学科关联是主要竞争方向；具体新颖性仍待比较验证。
- 用户表示团队对面向学习、由 teacher 导学的目标已基本认可，尚不将其表述为全部产品取舍均达成最终共识。
- 用户明确同意 teacher 在学习主线主动邀请用户表达自己的理解，并据此了解学习情况。具体表达形式与时机仍待讨论；不改变 keeper 关联卡只说明联系、展示旧内容的选择。
- 用户已确认主要体验：打开产品后，跟随 teacher 按大纲学习；同时允许主动横向展开，随时偏离主线并返回，teacher 在过程中持续辅助。
- 用户希望横向探索能够容纳兴趣、灵感及自主追问；其实际学习收益仍是待研究假设，不将每次探索都改造成测验。
- 用户已确认先让学习者阅读一些内容，但具体读什么、以何种形式呈现尚待讨论。用户反对直接提供枯燥资料或堆积大段文字，倾向 teacher 在资料导入阶段做相应处理，处理方式未定。
- 用户提议用按教材目录分组的子 agent 工作流处理长教材，避免把整本书塞进单次对话；主线允许跨小节、跨章重组和重排序，同一课程也可考虑把分散在不同册的内容串起来。助手建议原目录用于分派任务与回查，教学顺序根据目标及有依据的前置关系另行编排。
- 用户要求 teacher 在导入时主动问清会改变课程编排的要求，例如是否有外部时间约束、是否想给自己定期限；遇到说不清楚的用户，teacher 要给出带理由的推荐选项，明确方向后再编排。问题清单和呈现方式仍待讨论。
- 用户明确：「想系统学」、没有另行指定范围时，默认按全书范围编排。核心路线可以在已有节点上指出，供用户参考和自由选择，不能用它替代全书范围；系统内部也须保留核心路线。视觉表现和核心路线的判定、维护方式待议。
- 用户确定教材主线在整门课备齐后开放。导入时，teacher 完成全书编排，备好所有主线节点的学习目标、学习路径、知识点、引入和过关题。用户可把任务交给 teacher 后离开，完成后回来直接从想学的节点开始。
- 用户确认，教材主线开放后发现需要调整节点顺序或补充学习目标时，teacher 说明发现了什么、影响哪些地方，并给出修订建议。用户决定何时采纳，再应用到正在学的路线。
- 用户同意首版中，自己想调整教材主线的推荐顺序时，也由 teacher 按用户的意图提出修订，再由用户采纳。Teacher 核对改动涉及的前置知识和练习。
- 用户确认保留相对稳定的课程核心路线；备考或限时初学可另排优先顺序。应邀请用户提供任课老师划的重点、样题或其他能说明目标的资料；teacher 可按用户给出的线索联网补找公开资料。网络上的类似题仅供参考，不能据此断定本校本次考试的重点。
- 用户提出正式限时路线以至少一周为门槛：没有本课考核资料但还有至少一周，可以按教材编排基础路线；不足一周先给优先学习清单和外部资源，面向中国学生可优先推荐合适的 B 站视频，不把清单建成路线。若后续能可靠读取现成速成课，是否在该场景放宽门槛待议；按视频形成独立学习安排与系统学习原教材分开考虑。
- 临考清单给出后，用户仍可把看视频遇到的疑问、做过的题或写好的推导带回来，teacher 按平时的答疑和核查方式继续帮助。
- 主线中 teacher 应遵守当前学习大纲的范围与深度。课外内容只允许极少量提及，或提供用于简化当前计算的简单操作；这类操作可只讲用法，不在主线展开其超纲原理。
- 横向展开必须来自用户自己的意愿，不能由 teacher 自动把主线带入超纲教学；具体入口和界面交互暂后置。

| 预测候选学习节点，辅助后续学习安排，尤其考虑缺乏权威教材或成熟路线的自学 | 规划与记忆配合方式待定 |
| 根据学习笔记、草稿评价日常学习与进度，呈现进度条 | teacher |
| 与 LLM 对话，支持对话分支 | teacher |
| 在用户完成一句思考或推导后反向检查，提供分级、可展开的提示 | teacher |
| 学习结构支持 branch 与 merge；自动接回支线上下文，或由用户主动将成果汇到已有／新节点 | 具体职责待定 |
| 分支节点之间的交叉学习、关联与呼应 | keeper |
| 长期保存学习内容，包括学习记录、问题、笔记、反馈和试卷 | keeper |

- 用户明确要求：推导过程中不自动补全、不提前介入。teacher 可留意节点内写下的内容，发现已完成、足以单独检查的一段理解或推导，就主动核查；也可在原有的自由对话中按用户请求核查指定内容。用户把核查看作 teacher 可调用的一项能力，两条入口无需设计成两个模式。怎样识别一段已写完，留待交互设计。
- 用户认可：正式检查的反馈保存，并默认关联当时被检查的那版原文。用户修改后，teacher 复核通过可将相应提示标为已修正并收起；旧写法与当时的反馈保留供回查，旧反馈不再当作当前版本待修改的问题。
- 用户已确认主线／大纲推进程度与知识掌握程度分别呈现。具体显示形式、计算方式和掌握证据标准尚未确定，不把已阅读、已采纳候选或已完成安排直接等同于掌握。
- 用户确认全书、核心路线以及已经编排的备考等路线各自显示学习进度。每条路线按所含节点统计，同一个节点在多条路线中共用一份完成记录。
- 用户希望无主线学习用里程碑表示阶段目标和成果。探索图会继续生长，无需设置全图进度或按探索节点数计算阶段百分比。用户委托助手决定起步方式。首版默认由 teacher 按学习目标先拟一个最近、可观察的里程碑，用户可调整，先备好围绕它的连续几个节点。后续根据学习成果和目标的变化再立里程碑。达成的确认方式待讨论。
- 用户进一步划清：按提示把一处改对，只记录这次修正，不把它计入掌握判断。独立推导、解释或练习可提供掌握依据，证据标准另议。
- 用户同意跨节点使用掌握证据。Teacher 可以根据用户在其他节点里的独立表现，判断对应学习目标实际展示出的能力。原解答和学习事件归当时的焦点节点，掌握判断可回查那段解答。学习推进仍依据节点完成记录。
- 用户确认可以自行标记节点完成；已在实践或其他地方学过、没有提交当前节点的笔记或练习时也可以。自行标记只表达学习推进，不新增掌握证据，不覆盖已有判断；没有证据时仍为未判断。
- 用户明确：teacher 在编排教材主线时，为节点预先准备与学习目标对应的过关题。缺少独立表现时，teacher 可以主动邀请用户试做；用户主动要求自测、练习或核查时，teacher 也应在原有对话里帮助。过关题提供掌握证据，不阻止用户自行标记完成。题量、形式与课程级考试的安排后议。
- 用户确认大纲里的综合自测可做成独立的可选节点。开始前多次提醒时长及限制，最终确认后持续计时，焦点锁定至交卷。用户可确认后提前交卷，保存为本次正式作答并解除焦点锁定。
- 用户认可由 teacher 定开卷或闭卷，也提出可以在开考前商议。助手建议 teacher 按测验目标和已知考规提出默认条件，用户有需要可在最终确认前协商。资料条件改变时同步核对题目还能考查哪些能力。
- 用户确认考中由用户独立作答。Teacher 可回答规则和操作问题。遇到解题求助时，鼓励用户写下自己能想到的思路或不完整的步骤，也可以跳题，交卷后再核查和讲解。可依据用户实际独立写出的部分判断掌握情况。
- 用户要求最终确认开考后才显示试题。用户希望 teacher 在作答期间后台验题并准备讲解。用户发现疑点可先做其他题，teacher 核实后告知结果，确认题面有误时可在考中发布勘误。若发现错误时已来不及按勘误作答，用户确认按原截止时间交卷，作废该题并保留已写过程供复盘。
- 用户希望交卷后由 teacher 一步步带着讲题，成绩明显偏低时可根据答卷推荐回对应的知识节点复习。用户强调区分记不记得住和会不会用。助手建议先定位具体卡点，针对该学习目标补学后用新短题复测。用户确认可以先暂停讲卷、回看并补学相应知识，讲卷和这段补学都以自测节点为焦点。
- 用户允许直接跳到后续节点，teacher 起初按用户具备所需前置来讲；跳过不记为已掌握。强制回学仅限于「前置节点未完成、用户跳过它进入依赖它的节点、且经 teacher 判断反复卡住确由该前置缺口造成」三者同时成立。满足时直接带回具体前置节点补学；缺少掌握记录或重复提问本身都不足以触发。
- 用户强调教学要耐心，已经回去学过仍可继续问、继续讲，不用反复退回同一处。助手建议根据卡点换例子、拆步骤或先练操作；能按步骤做与能解释原理分别看，不把反复提问解释为能力上限。
- 用户提出的提示示例为“补充知识点”“理解有一定偏差”“错误”；分类和等级仍是草稿。
- 用户已认可检查覆盖概念理解、关键条件遗漏及推理逻辑，并强调由 teacher 发挥主动性、结合上下文综合判断。问题可能复合，同一表达可以同时涉及多种问题，不能强制只归入一类。
- 检查类别用于组织反馈，不能被实现为要求 teacher 单选标签的僵硬流程；具体反馈组织和严重程度表达仍待讨论。
- 用户允许 teacher 主动质疑并核查学习材料，但要求核查足够全面、准确；核查流程、充分性标准与不确定性处理仍待讨论。
- 教材作为课程范围和有效答题口径的基准。用户允许在导入时指出过时内容、补学习所需的遗漏、改正确认的错误。助手建议保留原文及出处，并区分争议、表述约定、时代差异和事实错误；无充分依据时标为待核。
- 用户要求解释与纠正的力度综合考虑错误严重程度和用户当前学习水平：问题越大通常越值得解释和修正，但学习水平是更强的讲解深度约束；超出用户当前理解能力时，即使问题严重，也应只简短提及，避免强行展开。
- 具体错误程度分级、解释篇幅和修改方式，用户明确要求后议，不在当前阶段设置固定阈值或字数。
- 用户总体认可简短、明确纠正的方向，但指出“提一嘴”也属于程度问题，当前讨论过于具体。具体纠正尺度与最低内容统一留待后议，不继续单独追问确认。
- 用户表示目前核心设想大致已经讲完，后续仍可增补；当前转入对完整项目的总体评价，不再追问是否还有未说功能，也不将大纲视为最终冻结。
- 用户已澄清 keeper 的“跨分支”：不同学科各自形成学习结构，系统发现其中知识点的前置关系或其他关联，提示用户把知识串联起来，并帮助回顾旧知识。
- 用户尚未确定“学习树”的组织方式；不要把严格树形结构当作已批准的数据模型。
- 上述跨学科知识关联与用户另行提出的“对话分支机制”需要分别定义；本轮澄清不代表取消对话分支功能。
- 用户进一步确认，节点树也用于承载主线与横向探索路径；不能仅把它理解为跨课程概念图。
- 用户把接回相关支线进展与主动带入成果都称为 merge，分别是自动与手动。有教材时倾向汇入已有节点；无主线时可把分散学习成果汇成新节点，作为阶段整理即可。想继续时，用户可在该节点问 teacher 下一步，并使用已有预测机制。
- keeper 的关联提示目前只需说明联系、展示旧内容。用户可就关联主动与 teacher 讨论，例如追问为何相关或表达新的想法。
- 用户认可关联的呈现分工：直接用得上的旧内容由 teacher 在讲解中引用；不必插进讲解但有具体联系的，可以由 keeper 单独轻量提示。只有题材或词语相似的结果留待按需查阅。
- 用户同意 keeper 独立发提示，teacher 先完成用户当前的请求，再检查提示是否合适，并可以撤回不合适的提示。撤回的对象是提示；模型是否相同不影响这条分工。
- 用户未采纳关联卡中的简短回忆／比较题候选方案，不将其作为默认交互继续推进。大纲中的考试、自测是原有的另一项功能，具体方式仍待讨论。
- 队友参考材料 `开发手册.md`，标题为《Knowledge IDE 开发规格》，文内日期为 2026-11-16。
- 用户另提供 `团队方案.docx`，标题为《Knowledge IDE 项目方案》。已读取正文、表格并检查其内嵌知识网络示意图。两份材料作为团队早期设计参考来评审。
- 用户本轮要求评价队友方案与其本人第 4 点的分歧，以及该方案单独参赛的竞争力。评价不能仅凭功能数量，也不能编造淘汰概率。
- 原案实际范围超出句尾补全，还包含概念提取去重、跨笔记关系、来源定位、主动探索、推测候选显隐和反馈记忆；不能将其简化为单一补全插件。
- 用户与队友沟通后进一步澄清，队友更完整的意图重在“预测节点”，面向自学的后续学习安排，不应继续以句尾文字续写概括这一方向。
- 用户希望将节点预测与 teacher 导学结合：面对缺乏比较权威教材或现成主线的领域，也能辅助组织下一步学习。
- 用户已进一步明确：目标场景是资料丰富但分散、没有成熟教材或现成学习路线；资料本身稀缺或尚待研究的领域不作为项目定位。
- 用户限定预测节点的出现范围：「无主线学习」沿着学习目标提出后续候选；有教材主线时，已创建的支线只可用候选继续当前范围内的探索。若新目标已经值得系统学习，teacher 应制止候选继续在原支线里扩张，并建议另开学习树。教材主线不出预测节点，当前目标内的答疑、检查和补讲仍由 teacher 负责。
- 节点预测只提供建议，以灰色候选节点展示。用户决定选或不选、选哪几个以及怎么选择；系统不因生成候选就自动调整主线或开始讲解。
- 用户已通过批注明确增加：展示预测候选后，由 teacher 推荐值得学习的节点，帮助用户选择，但不替用户决定。推荐应给出有帮助的理由，最终采纳权仍归用户。
- 用户希望首版无主线学习先试沿学习方向提前备好连续几个节点，让用户可以连续学一段。这里的深度指同一方向的后续步骤。候选继续由用户选择，具体准备深度可根据试用调整。
- “理解反馈怎样改善后续学习”是助手提出的候选教学支持机制，用户本轮要求详细解释；不能将其写成已被团队选定、取代节点化自由学习的唯一产品中心。
- 用户认为“理解反馈”这一名词听起来复杂。后续尽量用“根据你当前的理解来提供帮助”等直白说法，说明知识资料、个人学习记录与当前表达怎样共同影响解释和推荐。
- 灰色候选当前表达“尚未被用户采纳的学习建议”。不能未经讨论将其同时等同于内容不可靠、已经学过或已掌握；具体视觉与状态设计仍待后议。
- 此澄清改变了后续评审对象。先前针对句尾续写的竞争力结论保留其适用范围，不能直接用来否定节点预测与学习路径规划。

## 核心原则

**多查、多想、多问、多反驳。创新可以大胆，结论需要证据。**

- 直接、果断地评价方案，有问题就明确指出，不为了迎合用户而认可。
- 反驳应有证据、逻辑或可检验的理由，不为反驳而反驳。
- 不因保守而提前排除有潜力的新方向；允许提出具有风险、但值得验证的设计假设。
- 同样审视助手自己的方案，发现判断错误时明确修正。

## 讨论方式

- 收到团队思路后，通过多轮交流逐步完善设计。
- 每轮聚焦少数关键问题，通常提出 1—3 个问题，然后暂停，等待用户回答后再推进。
- 不要把所有问题一次性抛给用户；根据回答继续追问、验证或反驳。
- 关键需求、核心分歧和影响方案走向的假设，应与用户讨论，不擅自视为已经达成共识。
- 区分已确认的决定、待定问题和待验证假设，持续保留尚未解决的分歧。
- 在充分讨论团队思路后，主动提出助手自己的创新方向，并说明依据、风险和验证方式。
- 用户已要求先把混沌的产品设计聊通，再讨论具体验证。当前不继续催促选择课程、提供实验材料或安排学习效果实验；保留后续验证目标。
- 当前从完整学习过程梳理各项产品规则如何衔接。教材切分的具体粒度、节点阅读材料及其呈现、界面和实现留待后议。
- 用户再次强调当前讨论过于具体。多问应围绕整体定位、核心功能、角色分工和有实质取舍的问题，不把已认可的原则不断拆成小规则逐项确认。
- 最初第 4 点“表达／推导完成后的分级检查”已明确总体方向，应与其他功能统筹；具体分类、程度、篇幅和时机留待后续阶段。

## 检索与借鉴

- 主动进行网上检索，查找相关论文、开源项目、已实现的产品及可借鉴的设计思路。
- 随讨论深入进行针对性检索，不只在开始时搜索一次。
- 给出可核查的来源；技术判断优先参考论文、官方文档和项目仓库。
- 明确区分来源支持的事实、助手的推断和未经验证的假设。
- 比较已有方案与团队方案的相同点、差异及局限，审视所谓创新是否已有先例。
- 未检索到先例不足以证明首创；创新判断应说明检索范围和不确定性。

## 设计评审重点

- 学习对象与场景：谁在学习、学什么、目前卡在哪里。
- 学习机制：方案为什么可能有效，对学习者行为有什么要求。
- 人与 AI 的分工：系统如何促进学习者独立思考、练习和获得反馈。
- 可行性：实现成本、技术约束、使用阻力和潜在失败方式。
- 效果验证：如何检验独立解题、长期记忆或迁移应用等学习成果。
- 创新价值：相比已有方案，具体增加了什么能力，带来什么收益。

## 当前讨论阶段

用户倾向以有目标的问题或学习单元为节点，并明确提出三种体验：有教材时，teacher 在导入时读教材，编排主线节点并备好目标、节点内学习路径、知识点、引入与练习，用户进入后做笔记、写理解、问 teacher；自主支线因用户当下的问题而开，没有预先备课；预测节点是供用户选择的建议，teacher 可以在用户选择之前准备目标、路径和知识点。

用户已确认自主支线的开场：进去可以先写自己的问题或笔记，也可以主动问 teacher。teacher 按需提供帮助，打开支线时默认不主动安排学习步骤。

用户澄清，主要风险是原支线逐渐承载另一门本可按教材组织的课程，例如 ML 树下的神经网络支线长成整门 DL。可以不用故意讲难，但必须及时收住原支线里的课程式扩展；用户想系统学时另开学习树。助手建议在教学目标改变、后续开始需要独立大纲时判断是否收住；支线长度只提供检查信号。

用户选择：另开的学习树保留回到原节点的链接。学习记录、笔记、反馈和问题已经由系统持久保存，teacher 在任何学习树中都可以按需查询，无需为新树复制一份。链接让用户回看，也让 teacher 能准确找到新树的来路及当时的目标与上下文；新树当前的学习目标以用户的选择为准。

用户提出教材主线中没有前置依赖的章节可并行安排，按兴趣决定先学哪些，再继续需要这些基础的内容。接续已有综合节点由真实前置知识决定。用户将 teacher 自动接回相关支线进展称为自动 merge，将用户主动挑选学习成果汇入节点称为手动 merge。两者都保留原始记录；建议自动 merge 主要接续当前教学，手动 merge 则让成果在目标节点可见、可回查。

用户已确认无主线的手动 merge 可以只做阶段整理，无需同时决定下一步。之后想继续，可从整理好的节点问 teacher；若需要候选，沿用无主线学习的预测机制，由用户采纳。具体编排、状态与交互仍未冻结。

明确暂缓：教材切分的具体规则与粒度、节点阅读内容的呈现形式、节点字段与交互、branch／merge 的具体操作、具体错误程度与解释篇幅、公式输入与流程图等编辑体验优化、具体验证课程和学习效果实验。

当前阶段（2026-11-22 全局复盘）：核心产品规则已成形，正在从产品设计进入首版规格与工程设计。首版同时提供有教材主线和无主线学习，两种入口已有[验收流程草案](docs/product-outline.md#8-首版验收流程草案)。用户确认比赛版同时做[教材编排与验收、支线返回续学两段工作流](docs/product-outline.md#9-比赛版工作流)，演示主故事按完成度选择。接下来把两条用户流程、共用的学习图与记录、平台输入输出和验收条件写成统一的首版规格。教材编排质量、记录引用和平台运行效果待实测。

团队共三人。用户具备全栈能力，目前负责产品设计。用户委托助手安排首版分工，按一名前端、两位偏后端来排。两位队友分别主做网页和应用后端，用户主笔产品规格并负责教学与两段 AgentArts 工作流，后端队友牵头把网页、应用数据和工作流接起来。第一轮以共用样例并行实现和联调。[分工与交接底稿](docs/product-outline.md#10-三人分工与交接底稿)

用户要求重新设计 agent 的上下文与学习图如何配合，并关注跨节点时怎样找回前文。用户已确认同一时刻以一个节点为学习焦点。用户可以自由浏览、引用和询问其他节点的内容，产生的学习事件归到当时的焦点节点，并可回查用到的来源。用户确认主动开支线就把焦点切到支线。沿来路返回时，恢复出发时的焦点和位置，teacher 自动接回相关进展。助手提出按焦点、正在处理的问题和可回查的记录组装上下文，见[路径与 merge 讨论稿](docs/path-and-merge-draft.md#5-节点和-agent-的上下文)。
